# ESP-CAM setup

Implementation in the original Sightline checkout. The existing seven-step eye/scene calibration flow and per-profile mappings remain available under Eye Tracker Setup. ESP-CAM Setup adds an independently oriented third view, person-only selection, cross-camera person matching, explicit voice/button confirmation, and MQTT pan following.

The camera viewer reference is `gaze-three-camera-viewer`; firmware reference is ESP-CAM `codex/mqtt-servos`, commit `d67f4b3`. MQTT commands use the fixed `esp32cam/kate/servo/delta` topic on `broker.hivemq.com:1883`, QoS 0, retain false, signed integer relative degrees. Gyro telemetry keeps its separate topic. Video remains HTTP MJPEG; MQTT does not transport camera frames.

## Implementation sequence

1. Port tested object tracking, local voice, and model runtime without changing eye calibration.
2. Preserve USB, HTTP/HTTPS playable video, ESP port 81, and mDNS sources; add an authenticated MJPEG relay for non-CORS cameras.
3. Add a bounded, leased MQTT gateway. Selection and matching cannot move servos. Explicit Track requires recent reliable matches; missing/old evidence, disconnects, Stop, and leaving setup disarm it.
4. Add two setup segments, three previews, selection overlays, connection and model states, and local voice controls in Sightline's clay styles.
5. Test transforms, ownership, stale/repeated frames, delayed responses, cancellation, transport compatibility, and controller limits. Run type checks, frontend/Python suites, production build, and browser layout review.

## Deployment constraints

This uses one long-running Node process and a Python model companion, not an edge/serverless handler. The hosted server publishes directly to the embedded MQTT broker/topic; it does not need inbound connectivity to the ESP to publish. Multiple replicas require distributed device ownership before scaling. The device must run the firmware with the matching fixed topic.

Camera video needs its own reachable route. A cloud host cannot fetch a camera's private LAN address unless it joins that LAN through a VPN/tunnel. Use that network route for the authenticated MJPEG relay, or a browser-readable HTTP/HTTPS stream with CORS. The firmware reference does not serve CORS headers or publish video over MQTT.

Without reachable `/status`, the UI reports broker connection separately from device telemetry. A successful MQTT publish is not evidence of physical servo movement. Stop ceases new commands; the firmware holds its last PWM position. No firmware stop/acknowledgement command exists.

## Run and deploy

Prepare the runtime following [vision/README.md](../../vision/README.md), then run `bun run --cwd apps/web dev:tracking --port 3011`. For production, run `bun run --cwd apps/web build` and `bun run --cwd apps/web start:tracking`. Keep the `vision` directory, its prepared virtual environment, `.local-reference/vision-models`, and generated browser runtime assets alongside the deployment. Standard `dev`/`start` keep eye calibration available without starting the optional Python companion.

Container deployments can select the `tracking` target in `apps/web/Dockerfile` to build the Python environment and model files into the web image. The default target remains the existing standalone web image. See the companion README for build arguments, runtime requirements, and the outstanding Linux container smoke test.

Set `SIGHTLINE_APP_ORIGIN` to the public HTTPS origin behind a reverse proxy and `SIGHTLINE_SERVER_URL` to the trusted Sightline API server if it differs from `NEXT_PUBLIC_SERVER_URL`. Forward authentication cookies to Next and the API under the same deployment domain. Hosted camera endpoints require a real signed-in account; mock authentication is limited to localhost. Keep outbound MQTT TCP port 1883 reachable. Broker/topic defaults are in `apps/web/src/features/esp-camera/server/configuration.ts`; server-only environment overrides are available for another firmware deployment.

Object selection is ephemeral and cleared when leaving the ESP segment. Camera URL and pan preference persist per signed-in profile in this browser; connections and physical following never restart automatically. Eye/scene calibration retains its existing per-profile save/new/replace/reuse behavior.

The calibrated eye-to-scene measurement is the selection cursor in the Scene view. It already includes the scene orientation and gaze offset; it is not projected directly into the independent ESP viewpoint. With voice enabled, “select” reads the current session at command time and chooses a detected person's body at that point. The Select at gaze button uses the same smoothed cursor. Missing, unlocked, out-of-frame or stale gaze cannot fall back to the center or a previous mouse position. A brief gap retains a faded display cursor for at most 350 ms from its original eye timestamp; that held cursor cannot select anything. Unverified mappings remain explicitly labeled as previews. Click/drag selection must also resolve to one detected person. Selection never starts servo motion; the user verifies the person in ESP-CAM and separately says “track”.

The controller sends only X deltas, at most 6° per 250 ms, with a 6% center deadband. Two distinct verified frames are required before Track. Person evidence carries the actual OSNet cosine (at least 0.65), separation from the next person (at least 0.08), and person detector confidence (at least 0.3). These are evidence scores, not an identity accuracy percentage. Generic reference evaluation retains its original 0.8 threshold. Evidence older than 500 ms cannot command movement. A person follow request pauses after 750 ms without fresh evidence, retains its original two-second recovery deadline, and requires two fresh observations to resume; expiry disarms it. A display-only amber body box can remain for 1.2 seconds without renewing control evidence. Ordered control intents prevent delayed responses from overriding Stop. Clock translation accounts for hosted-server/browser clock differences; repeated frames cannot renew motion. Loss of the broker, selection changes, hidden tabs, navigation, and sign-out stop following. The Positive X moves camera left setting is enabled for Kate’s mount. Change mount direction only while stopped/disconnected.

## Person identity and network continuity

The app's vision proxy forces `kind: person` for every selection. YOLO26s proposes only COCO person detections. OSNet-AIN MSMT17 produces a body-appearance descriptor from the selected Scene crop; an immutable normalized anchor is retained in the expiring session. Selection seeds the Scene lock immediately and returns a small reference JPEG from that exact frame. A failed replacement preserves the previous reference. Torso rectangles resolve by coverage within a detected person, so users do not have to trace the detector's complete body box.

Target acquisition requires two observations. Each camera retains its own immutable confirmed descriptor, requires appearance and spatial continuity, and remembers distinct visible bystanders. Identity margin includes these remembered negatives even when the original person leaves. The same-camera cosine floor is 0.8, in addition to the cross-camera anchor floor of 0.65. These are conservative rejection rules, not biometric identity guarantees. A brief gap can recover at the previous location within two seconds; an established Target lock missing for longer latches `lost`, clears all movement evidence, stops following, and requires explicit reselection. Scene loss stops updating that view without erasing the reference or an independently verified Target lock. No automatic appearance adaptation or identity reassignment is allowed. No face recognition or persistent identity database is used. The old generic-object engine remains available only for reference evaluation and loads its models lazily; the app cannot select arbitrary objects.

Independent eye and Scene streams now pair against the nearest fresh buffered Scene observation for the newest decoded eye evidence. A Scene arrival ahead of its eye worker no longer creates an artificial lost-gaze sample. Original timestamps, freshness/skew limits, pupil-loss rejection and recording validity remain strict. Cursor smoothing and brief visual holds never alter calibration evidence or refresh sample age. Person selection distinguishes camera identity (source connection epoch + transform) from decoded-observation generation: a 1.5-second network freshness reset discards old movement evidence but retains the reference and same-camera matcher. A late result from before that reset cannot renew movement. A genuinely replaced, previously locked Target camera requires reselection.

The earlier replay's high match coverage did not establish identity accuracy: the live report exposed a sole-bystander false-accept path that those checks missed. Regression tests now reproduce replacement failure, similar newcomers at the same position, remembered bystanders seen alone, bounded gap recovery, and a latched loss. The stricter 5 fps replay returns 59 matched / 11 searching / 18 lost dark samples, latching at 14 s during the obscured view; the hazy replay returns 100 matched / 24 searching / 3 ambiguous without a latched loss. All 159 accepted crops were reviewed visually and show the selected person. This small, manually reviewed replay is not a general identity accuracy guarantee. Private clips/replays remain outside tracked sources. Automated regression/model checks do not publish to the physical servo topic; the separately authorized hardware replay is recorded below. Verification: 313 frontend tests, 180 vision tests, TypeScript, Ruff and production build pass. The build retains the existing Varlock dynamic-import warning. The live saved network-camera URL was unreachable during the final browser check, so connected-camera and physical-servo validation remain outstanding.

## Model comparison — 23 October 2026

Compared the installed [OSNet-AIN MSMT17](https://github.com/KaiyangZhou/deep-person-reid) with the authors' [FastReID SBS ResNet50-IBN MSMT17](https://github.com/JDAI-CV/fast-reid/blob/master/MODEL_ZOO.md). The latter was evaluated separately, not installed into production. Official source revision: `c9bc3ceb2f7a6438b62fb515ea3df6d1e999e95d`; official checkpoint SHA-256: `4e10cfb5dc667df0ff448838df6f9b56c9d10a95b5349bb9afebaf241a16de4a`. Its older `heads.bnneck` names were mapped to the current `heads.bottleneck.0`; all inference tensors were validated, and only the unused training classifier was omitted.

The private probe used 64 detected crops from 43 frames sampled one second apart in the two supplied, unsynchronized recordings. Crop labels were reviewed manually: 41 selected-person crops excluding the selection frame and 22 bystanders. The reference is the hazy recording at 5 seconds. This is a small diagnostic sample from one room, not a held-out general benchmark.

| Measurement | OSNet-AIN | FastReID SBS R50-IBN |
| --- | --- | --- |
| Warm feature extraction median / p95, fixed padded batch of four on MPS | 34.8 / 45.5 ms | 44.3 / 60.7 ms |
| Selected person in dark view, cosine range | 0.657–0.802 | 0.331–0.607 |
| Selected person in hazy view, cosine range, excluding reference | 0.800–0.961 | 0.601–0.929 |
| Bystanders, cosine range across both views | 0.425–0.668 | −0.004–0.367 |

Cosine scales differ between models; lower bystander scores alone do not establish a superior model. Both have overlapping global selected/bystander score ranges under the exposure change. No threshold was tuned or deployed from this sample. Feature timings exclude detection, video decoding, HTTP and gaze processing. Current recommendation: retain OSNet while repairing identity retention; a larger replacement has not yet demonstrated sufficient benefit on this footage.

[KPR (ECCV 2024)](https://github.com/VlSomers/keypoint_promptable_reidentification) is the most relevant next experiment for overlapping bodies: it matches visible body parts and can use positive/negative skeleton prompts to specify the intended person in a mixed crop. It needs a pose stage and separate latency/domain testing; its repository uses the Hippocratic License 3.0 rather than MIT. [CLIP-ReID](https://github.com/Syliz517/CLIP-ReID) is another research candidate, but its published benchmark performance is not evidence for this room, camera pair, or network latency. Neither has been evaluated or deployed here. Severe blur, clipping and occlusion still require abstaining rather than assigning the nearest-looking person.

Automated validation uses injected transports and synthetic/public-image fixtures without publishing movement commands. A separately authorized recording-to-MQTT hardware test is described below. Complete a supervised hardware check for the actual mount direction, video route, lens/viewpoint, and target speed before relying on live following.

## X direction, adaptive correction, and MQTT verification — 23 October 2026

Kate confirmed that positive X turns left and negative X turns right. The default now enables X inversion in both the browser and controller. Version 2 camera preferences retain the previous URL while adopting this corrected mount default; explicit version 2 direction preferences remain respected. Y direction and Y movement are unchanged: following publishes only X. The firmware accepts an omitted Y as zero delta and does not rewrite its PWM in that case.

The pan response uses the person’s distance from the sensor image center. Inside a 6% horizontal deadband it stops correcting. Outside, a bounded nonlinear curve increases requested speed from 0.8°/second toward 12°/second, reaching full speed at a 35% offset. Whole-degree deltas are limited to 3° per 250 ms. Fractional corrections accumulate between fresh observations so small offsets produce spaced one-degree movements rather than a compulsory move on every frame. Center entry, direction reversal, Stop, and tracking loss discard fractional carry. Elapsed time accounts for ordinary network frame-rate differences, and accumulated stall time cannot cause a catch-up burst.

A four-second controller simulation requested 4°, 10°, 26°, and 48° at fixed 8%, 15%, 25%, and 35% offsets respectively. These are requested open-loop totals, not measured hardware speeds. The recorded dark-view detections produced seven correction packets, no larger than 2°, with this curve. Tests cover near-center pacing, increasing response, direction changes, clearing carry in the deadband, and 2 Hz versus 20 Hz input.

Before this curve was added, Kate explicitly authorized a physical test using the supplied videos. The production vision model selected the person from the hazy clip and matched 59 frames in the dark clip. The production controller/gateway published eight X=-1 packets to broker.hivemq.com:1883 on esp32cam/kate/servo/delta, then compensating X=+3,+3,+2 packets. An independent MQTT subscriber received all 11 packets. Final net requested displacement was zero, and every packet was X-only. Kate observed a small X movement and substantial Y wobble. This confirms physical command delivery, but does not validate accurate centering or resolve the Y wobble. The firmware parser/runtime host tests pass, including single-axis position/PWM preservation. Device-side logs or measurements are still needed to explain the wobble. No firmware sources were changed.

The setup page’s live target stream remained disconnected while the broker was connected. A direct status request to esp32.local failed hostname resolution. The relay now bounds hostname lookup at two seconds and reports the numeric-IP remedy. Reconnection reports its current cause immediately, while retaining automatic recovery and cancellation, instead of hiding the cause throughout all retries. Kate will configure and test the live feed separately. Recorded video can verify model/controller/publisher behavior but cannot validate closed-loop centering because servo motion does not alter its frames.

Final verification for the adaptive controller: 322 frontend tests, standalone TypeScript checking, and the production Next build pass. Existing firmware command and runtime host tests also pass. The development server was restarted from the original Sightline checkout on port 3011 to activate the new controller.

Kate subsequently requested another hardware replay with the adaptive curve, and explicitly chose to keep Y disabled. No vertical-following code was added. After Kate confirmed that the replay's X movement was still too small, the normal correction limit increased from 3° to 6° per 250 ms.
